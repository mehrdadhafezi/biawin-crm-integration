## 0. AUTHORITATIVE CUSTOMER JOURNEY — FINAL

CRM اساساً چرخه **رضایت‌سازی** مشتری است. این Journey **قرارداد کسب‌وکاری محافظت‌شده** است: بازتفسیر، «بهینه‌سازی» به مدل دیگر یا ادغام مفاهیم جدا ممنوع است. هر جا کد فعلی (0.8.64.1) با آن منطبق نیست، فاصله در §0.7 به‌صورت CURRENT / TARGET / GAP / PHASE ثبت شده است؛ **هیچ ادعایی مبنی بر پیاده‌سازی فعلی این قواعد در این سند وجود ندارد مگر در §0.7 با علامت ✅.**

### 0.1 مفاهیم جدا — هرگز ادغام نمی‌شوند

| # | مفهوم | مقادیر کسب‌وکاری | محل نگهداری (موجود) | مالک |
|---|---|---|---|---|
| 1 | وضعیت پروفایل (`profile_completeness`) | **کامل** · **ناقص** — فقط دو وضعیت کسب‌وکاری | `customers.profile_completeness` = `complete` / `incomplete`. مقدار فنی `pending` (هنوز مبلغ اعلامی ثبت نشده) وضعیت کسب‌وکاری سوم **نیست** | CRM Core |
| 2 | رفع ناقصی (`deficiency`) | گردش‌کار جدا برای پروفایل ناقص؛ تأیید مالی (`finance verification`) مسیر **اختیاری** داخل آن | `deficiency_cases`، `case_actions` (دپارتمان `deficiency` / `finance`) | CRM Core |
| 3 | مسیر مشتری (`journey_state`) | **ناراضی** · **بدون خدمات** · **خدمات مازاد** — فقط سه مسیر | `customers.journey_state` = `complaint` · `no_request` · `service_request` | CRM Core |
| 4 | نتیجه نارضایتی (`resolution_outcome`) | عودت (`refund`) · تهاتر (`offset`) · سایر نتایج کاتالوگ Admin | `complaints.resolution_outcome` + کاتالوگ Outcome | دامنه نارضایتی (فاز ۳) |
| 5 | وضعیت پرونده نارضایتی (`complaints.state`) | چرخه مستقل پرونده (سند ۰۳) | `complaints.state` | دامنه نارضایتی (فاز ۳) |
| 6 | یکپارچگی بیرونی خدمات مازاد (`additional services integration`) | مرز API / Web Service به سامانه Biawin | — (قرارداد جدا؛ §0.5) | مرز Core |

هیچ ستونی بیش از یک مفهوم را نگه نمی‌دارد؛ هیچ مفهومی در Tag یا ستون دیگری بازتعریف نمی‌شود. نابرابری‌های قفل‌شده:
- مسیر مشتری ≠ نتیجه نارضایتی
- خدمات مازاد ≠ نارضایتی (Complaint)
- خدمات مازاد ≠ تهاتر
- تأیید مالی ≠ تکمیل رفع ناقصی
- وضعیت پروفایل ≠ وضعیت پرونده نارضایتی

### 0.2 Journey نهایی

**نسخه مرجع (قفل‌شده، عیناً):**
```text
Customer enters CRM → Initial contact → Declared amount → Compare declared amount with total invoice amount
   ├─ Mismatch       → INCOMPLETE → Deficiency Workflow → Profile becomes COMPLETE → COMPLETED_AFTER_DEFICIENCY
   │                   → Supervisor Allocation Queue → Assignment to Contact Agent → NEW CONTACT → Customer Route Selection
   └─ Difference = 0 → COMPLETE   → Customer Route Selection
Customer Route Selection:
   Dissatisfied        → After-Sales → Complaint → Outcome
   No Service          → Archive
   Additional Services → API → Biawin CRM → Continue Operations
```

قواعد کسب‌وکاری:

| # | قاعده |
|---|---|
| J1 | هر مشتری دقیقاً یک پروفایل در CRM دارد؛ شناسه مشتری (`customer_id`) در کل چرخه ثابت است؛ هیچ موجودیت مشتری دوم. |
| J2 | مقایسه مبلغ اعلامی با مجموع فاکتورها **فقط** وضعیت پروفایل را تعیین می‌کند: برابر → کامل؛ نابرابر → ناقص. |
| J3 | پروفایل کامل در همان تماس: مسیر مشتری بلافاصله برای کارشناس تماس باز می‌شود (بدون رفع ناقصی). |
| J4 | پروفایل ناقص: مسیر مشتری **در دسترس نیست**؛ مشتری وارد رفع ناقصی می‌شود. |
| J5 | رفع ناقصی ≠ تأیید مالی. کارشناس رفع ناقصی مغایرت را بررسی می‌کند و آن را **مستقیم** حل می‌کند یا **در صورت نیاز** به تأیید مالی می‌فرستد (و ممکن است به رفع ناقصی بازگردد). تأیید مالی مرحله اجباری هر پرونده نیست. |
| J6 | پایان رفع ناقصی: پروفایل **همان** مشتری کامل می‌شود؛ فاکتورها و مالکیت‌شان ثابت. |
| J7 | پس از تکمیل: تگ «تکمیل‌شده پس از رفع ناقصی» (`COMPLETED_AFTER_DEFICIENCY` — تگ موجود، reuse) ثبت می‌شود. |
| J8 | پس از تکمیل: مسیر مشتری **نه** برای کارشناس رفع ناقصی باز می‌شود **و نه** خودکار برای کارشناس تماس قبلی؛ مشتری به صف تخصیص توسط سرپرست بازمی‌گردد (موتور تخصیص موجود). |
| J9 | سرپرست مشتری را به یک کارشناس تماس تخصیص می‌دهد؛ **تماس جدید اجباری** است؛ تماس قبلی مسیر جدید را تعیین نمی‌کند؛ پس از تماس جدید مسیر مشتری باز می‌شود. |
| J10 | مسیر مشتری دقیقاً سه گزینه مانعةالجمع دارد: ناراضی · بدون خدمات · خدمات مازاد؛ انتخاب‌کننده: کارشناس تماس. |
| J11 | ناراضی → خدمات پس از فروش → پرونده نارضایتی (`complaint`) → بررسی → نتیجه نارضایتی. |
| J12 | بدون خدمات → ثبت نتیجه «بدون خدمات» → بایگانی بدون خدمات (`no-service archive`) → **پایان چرخه فعال**. حذف نیست؛ پروفایل در CRM می‌ماند و قابل جست‌وجو است؛ مرحله بعدی مصنوعی ندارد؛ فقط فرایند آتی صریح می‌تواند آن را دوباره باز کند. |
| J13 | خدمات مازاد → کارشناس تماس خدمات را از کاتالوگ خدمات موجود انتخاب می‌کند → ارسال به سامانه Biawin از طریق API / Web Service؛ چرخه پایین‌دست (اشتراک ← خدمات/کارت‌ها ← صف و سرپرست اختصاصی هر خدمت) در سامانه بیرونی ادامه می‌یابد. **تنها** مسیری که وارد یکپارچگی Biawin می‌شود. |
| J14 | خدمات مازاد ≠ تهاتر (§0.3). تهاتر یکی از مسیرهای مشتری نیست. |
| J15 | عودت (`refund`) لایه نتیجه نارضایتی است، نه مسیر مشتری؛ `journey_state='refund'` مسیر مشتری نیست (رفتار legacy — §0.7). |
| J16 | پرونده نارضایتی (Outcome، Action، Inquiry، Refund، Offset، Follow-up، Resolve، Close، Reopen) هرگز مسیر مشتری (`journey_state`) را تغییر نمی‌دهد؛ مسیر پیش از شروع نارضایتی انتخاب شده است. |
| J17 | وضعیت پروفایل مفهوم Core است؛ نارضایتی آن را تعیین نمی‌کند و Gate رفع ناقصی را دور نمی‌زند؛ پروفایل ناقص از مسیر عادی وارد نارضایتی نمی‌شود. |
| J18 | سرپرست مسئول تخصیص هر دو گروه است: مشتریان اولیه و «تکمیل‌شده پس از رفع ناقصی»؛ تمایز با تگ/تاریخچه؛ هیچ موتور تخصیص موازی و هیچ دور زدن تخصیص سرپرست. |

### 0.3 مسیر مشتری در برابر نتیجه نارضایتی — خدمات مازاد ≠ تهاتر

| | مسیر مشتری (`journey_state`) | نتیجه نارضایتی (`resolution_outcome`) |
|---|---|---|
| مرحله | پس از تماس با پروفایل کامل | پس از بررسی پرونده نارضایتی (فقط در مسیر ناراضی) |
| انتخاب‌کننده | کارشناس تماس | کارشناس نارضایتی |
| گزینه‌ها | ناراضی · بدون خدمات · خدمات مازاد (ثابت) | عودت · تهاتر · مشتری راضی شد · پیگیری مجدد · سایر (کاتالوگ Admin) |
| مالک | CRM Core | دامنه نارضایتی |
| اثر بر دیگری | «ناراضی» پرونده نارضایتی را باز می‌کند | **هیچ** — هرگز مسیر مشتری را تغییر نمی‌دهد |

| | خدمات مازاد (`additional services`) | تهاتر (`offset`) |
|---|---|---|
| نوع | یکی از سه **مسیر مشتری** | یکی از **نتایج نارضایتی** |
| زمان | پس از کامل شدن پروفایل | داخل خدمات پس از فروش، پس از بررسی پرونده |
| انتخاب‌کننده خدمت | کارشناس تماس | «واحد تهاتر» (`offset unit`) |
| کاتالوگ | کاتالوگ خدمات موجود (منبع حقیقت) | ممکن است از همان کاتالوگ و زیرساخت داخلی خدمات استفاده کند (و خدمات مخصوص رضایت‌سازی) |
| یکپارچگی API / Biawin | **تنها** مسیری که وارد یکپارچگی خدمات مازاد می‌شود | **خارج** از یکپارچگی خدمات مازاد؛ هرگونه استفاده آتی تهاتر از Biawin فقط با تصمیم کسب‌وکاری جداگانه و تأییدشده (AMB-9) و نه زیر این یکپارچگی |
| اثر بر `journey_state` | `service_request` | **هیچ** (مسیر «ناراضی» می‌ماند) |

ممنوع: مدل‌سازی تهاتر به‌عنوان خدمات مازاد؛ مسیر مشتری دوم برای تهاتر؛ موتور تهاتر (مگر با تصمیم تأییدشده بعدی)؛ قرار دادن API / Biawin زیر ناراضی، نارضایتی، خدمات پس از فروش، عودت یا تهاتر.

### 0.4 رفع ناقصی → کامل → تخصیص مجدد (Deficiency → Complete → Reallocation Flow)

```text
پروفایل ناقص (مغایرت ≠ 0)
↓
رفع ناقصی: بررسی توسط کارشناس رفع ناقصی
   ├─ (الف) حل مستقیم (ارتباط/بررسی با مشتری)
   └─ (ب) در صورت نیاز: ارسال به تأیید مالی → (بازگشت به رفع ناقصی در صورت نیاز)
↓
مغایرت برطرف شد → همان شناسه مشتری (customer_id): وضعیت پروفایل = کامل
↓
تاریخچه: تگ «تکمیل‌شده پس از رفع ناقصی» (COMPLETED_AFTER_DEFICIENCY) + completion_source + deficiency_cases/case_actions
↓
بازگشت به صف تخصیص توسط سرپرست:
   تخصیص فعال قبلی کارشناس تماس (assignments.status='assigned') → 'returned'   ← همان وضعیت و سازوکار موجود «برگشت تخصیص»
   مشتری در استخر «بدون تخصیص فعال» صفحه «تخصیص پرونده» با فیلتر «تکمیل‌شده پس از رفع ناقصی» ظاهر می‌شود
↓
سرپرست با همان موتور تخصیص (assignments) به کارشناس تماس تخصیص می‌دهد
↓
تماس جدید (interaction کارشناس تخصیص‌یافته پس از زمان تکمیل رفع ناقصی)
↓
مسیر مشتری: ناراضی / بدون خدمات / خدمات مازاد
```
- چگونگی دریافت صف توسط موتور تخصیص موجود: موتور فعلی برای هر مشتری حداکثر یک تخصیص فعال (`assigned`) دارد (Guard دیتابیسی موجود) و استخر سرپرست «مشتریان بدون تخصیص فعال» را نشان می‌دهد. بنابراین تنها کار لازم، بستن تخصیص فعال قبلی با وضعیت موجود `returned` (همان عمل «برگشت تخصیص» صفحه سرپرست) و افزودن فیلتر تگ است — **بدون** موتور یا جدول تخصیص جدید.
- کارشناس رفع ناقصی تخصیص تماس دریافت نمی‌کند و مسیر مشتری را انتخاب نمی‌کند؛ کارشناس تماس قبلی خودکار ادامه نمی‌دهد؛ مسیر هرگز خودکار پس از تکمیل انتخاب نمی‌شود.
- **وضعیت دقیق تخصیص در این گذار:** `assignments.status` از `assigned` به `returned` (+ `completed_at`) — همان وضعیت و سازوکاری که امروز «برگشت تخصیص» صفحه سرپرست (`bcrm_return_assignments`) استفاده می‌کند. وضعیت جدیدی تعریف نمی‌شود (هیچ دلیل فنی برای عدم استفاده از `returned` وجود ندارد).
- مشتری در صف سرپرست به‌عنوان «نیازمند تخصیص مجدد» دیده می‌شود: «بدون تخصیص فعال» **و** تگ `COMPLETED_AFTER_DEFICIENCY`.
- حفظ کامل: همان `customer_id`، فاکتورها، همه `deficiency_cases`/`case_actions`، همه `assignments` (ردیف `returned` قبلی می‌ماند) و همه `interactions`.

### 0.5 مرز یکپارچگی خدمات مازاد (Additional Services Integration Boundary)

```text
CRM → مسیر «خدمات مازاد» → انتخاب خدمات توسط کارشناس تماس → کاتالوگ خدمات CRM (service_catalog — منبع حقیقت)
    → API / Web Service   ← مرز
    → سامانه بیرونی Biawin (ادامه چرخه پایین‌دست خدمات)
```
- **تنها** مسیر مشتری که وارد این یکپارچگی می‌شود «خدمات مازاد» است. یکپارچگی API / Biawin زیر ناراضی، نارضایتی، خدمات پس از فروش، عودت یا تهاتر قرار نمی‌گیرد.
- **مدل خدماتی Biawin (شرح کسب‌وکاری، نه قرارداد API):**
  ```text
  مشتری → اشتراک (Subscription) → چند خدمت (Service؛ در UI به‌صورت «کارت» — مثلاً ۱۰، ۱۲، ۱۵ یا بیشتر)
        → هر خدمت/کارت انتخاب‌شده → صف عملیات مخصوص همان خدمت → سرپرست مخصوص همان خدمت → گردش‌کار مخصوص همان خدمت
  ```
  یکپارچگی آینده باید این مدل را به‌صورت مفهومی پشتیبانی کند: مشتری ← اشتراک ← خدمات/کارت‌های انتخاب‌شده ← صف و سرپرست اختصاصی هر خدمت.
- **دامنه مشتریان:** یکپارچگی هم مشتریان **جدید** و هم مشتریان **موجودی** را که امروز مسیر خدمات مازاد دارند (`journey_state='service_request'` با `service_cases` موجود) پوشش می‌دهد. الزامات معماری (بدون تعریف پیاده‌سازی): ایجاد اولیه، همگام‌سازی، تطبیق (Reconciliation)، Idempotency و جلوگیری از تکرار مشتری/اشتراک/خدمت در Biawin. فرض نمی‌شود که هر مشتری ورودی جدید است.
- فاز ۳.۱ هیچ Endpoint، فیلد، جدول بیرونی، نگاشت شناسه یا پیاده‌سازی تعریف نمی‌کند؛ قرارداد API پس از بررسی سند اختصاصی Web Service سامانه Biawin جداگانه طراحی می‌شود.
- هیچ کاتالوگ خدمات دوم.

### 0.6 مرز دامنه نارضایتی (Complaint Domain Boundary)

```text
CRM CORE ── مالک: پروفایل مشتری · فاکتور و مالکیت آن · کامل/ناقص · رفع ناقصی · تأیید مالی پروفایل · تخصیص توسط سرپرست · مسیر مشتری · بایگانی بدون خدمات · خدمات مازاد
   پروفایل → کامل/ناقص → (ناقص: رفع ناقصی → کامل → صف سرپرست → تماس جدید) → مسیر مشتری
                                                                            ↓
                                                                  ┌──────────────┐
                                                                  │    ناراضی    │
                                                                  └──────┬───────┘
                                                                         ↓
                                                              خدمات پس از فروش
                                                                         ↓
PHASE 3 ── مالک:                                                  پرونده نارضایتی
   استعلام · تصمیم (نتیجه) · اقدام‌ها · عودت · تهاتر · پیگیری مجدد · خزانه
```

## 4. Conflictهای حل‌شده

### 4.1 C1 — دو فیلد وضعیت پرونده
`state` منبع حقیقت؛ `status` Projection (`closed` ⟺ `state ∈ {RESOLVED, CLOSED}`).

### 4.2 تهاتر روی زیرساخت موجود خدمات
```text
پرونده نارضایتی → نتیجه «تهاتر» (service_request، requires_offset=1)
   → اکشن SERVICE_OFFSET (assigned_unit_id = «واحد تهاتر»)
   → عضو واحد تهاتر خدمت(ها) را از کاتالوگ خدمات موجود انتخاب می‌کند
   → Workflow_Service::create_service_cases(customer, service_ids, note)   ← تابع مشترک (3.5)، بدون نوشتن journey_state
   → service_cases.complaint_action_id = اکشن → اکشن COMPLETED
```
- `select_services()` (مسیر خدمات مازاد) در 3.5 فقط داخلی Refactor می‌شود (`create_service_cases()` + `journey_state='service_request'`) و خروجی‌اش عیناً حفظ می‌شود.
- مسیر مشتری پرونده تهاتر «ناراضی» می‌ماند.
- تهاتر خارج از یکپارچگی خدمات مازاد است؛ پرونده‌های خدمت تهاتر در چرخه داخلی خدمات می‌مانند. هرگونه استفاده آتی از Biawin برای تهاتر فقط با تصمیم کسب‌وکاری جدا و تأییدشده (AMB-9) و نه از طریق یکپارچگی خدمات مازاد.
- اثر بر اعتبار خدمات: AMB-5. «انجام خدمات» (`SERVICE_FOLLOWTHROUGH`) خدمتی نمی‌سازد (AMB-3).

### 4.3 ثبت پرونده
```text
مسیر مشتری «ناراضی» (پروفایل کامل؛ پس از رفع ناقصی: صف سرپرست + تماس جدید)
   → set_customer_journey(customer,'complaint')   ← Core
   → Complaint_Service::create(): پیش‌شرط journey_state='complaint' و profile_completeness='complete' (R-1)
```
- `journey_state='complaint'` سابقه تصمیم مسیر Core است؛ دامنه نارضایتی آن را تغییر نمی‌دهد.
- اقدام «تأیید مالی» (`FINANCE_VERIFICATION`) نارضایتی (تأیید مبلغ عودت) با تأیید مالی رفع ناقصی یکی نیست و هیچ‌وقت `profile_completeness`، `declared_paid`، `financial_cases` یا `deficiency_cases` را تغییر نمی‌دهد.

### 4.4 C4 — Ledger
`refund_registers` Ledger اسنپ‌شاتی Excel؛ CRM در آن نمی‌نویسد (۰۲ §7).

### 4.5 C9 — گذار Visibility
امروز همه پرونده‌های باز `owner_user_id = NULL`. چک‌لیست: ۰۵ §7.

### 4.6 استقرار مرحله‌ای (Engine Switch)
Migrationهای 3.2–3.6 additive؛ رفتار جدید با `biawin_crm_complaint_engine ∈ {legacy, v3}`:
- `legacy`: رفتار 0.8.64.1، شامل تغییر مسیر مشتری توسط `resolve_complaint()` legacy (G8/G9) که با J16 مغایر است و فقط تا Cutover می‌ماند.
- `v3` (یک‌طرفه): پس از CJA، پیش‌شرط‌های ۰۵ §7 و `is_selectable` همه Outcomeهای فعال (۰۳ §6).
